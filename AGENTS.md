# Vivicy — agent guide

Vivicy is a **web app** — see [README](./README.md). This package has two parts:

- `factory/` — standalone Node ESM tooling: extraction, the dev-loop orchestrator and its resumable supervisor, the gates, the agent prompts (`prompts/`, one file per leg role), the target scaffold templates (`templates/`). Keep it plain `node` with no Next coupling — it has its own `factory/tsconfig.json` and a Node `--test` suite, and is excluded from the Next app's TypeScript and ESLint configs on purpose. Never add a progress MCP or a lifecycle-hook seam: agents never report progress; the orchestrator alone writes the ledger (`progress-ledger.ts`, the single source of truth for progress).
- `app/`, `components/`, `lib/` — the Next.js App Router control plane that drives the factory and renders the architecture map. The map is a static graph generated once at extraction and never regenerated per issue; `app/api/map/route.ts` overlays the live ledger (`lib/development-overlay.ts`, `lib/map-data.ts`) at read time.

The factory operates on a **target project**. The app resolves it in order: the project the user picked in the UI (persisted in the runtime dir) → the `VIVICY_TARGET_ROOT` env var → the parent of the process cwd (`..`). Vivicy is standalone, not vendored into the target. Never hardcode machine-specific paths.

Gates: `npm run typecheck`, `npm run lint` (ESLint, then `npm run format:check` through its `postlint` hook), `npm run test`, `npm run build`, `npm run e2e` for the app; `npm run factory:typecheck` and `npm run factory:test` for the factory; `node factory/dev-rehearsal.ts --dry` for the end-to-end method rehearsal.

Always run tests through the wrapped npm commands, never `npx vitest`/`npx playwright test` directly: only the wrappers clean the transient artifacts (`.next-e2e-*` dist dirs, `test-results/`, `playwright-report/`, Playwright's post-teardown `.last-run.json`). Targeted runs pass through: `npm test -- <test files>`, `npm run e2e -- <spec> --project=<project>`.

Confirm App Router APIs and conventions against the bundled docs in `node_modules/next/dist/docs/`, never from memory — the pinned Next major breaks with older releases.

## Method invariants (bind every change to this repo)

The workflow contract is implemented and locked by tests; **the code is the contract** — never maintain a sidecar document that re-describes what the project is (the durable "why" lives here, the rest lives in code, tests, and `git log`). This repo is **public**: the local method backlog (`TASKS.md`) stays gitignored, and nothing session-internal gets committed. Before any sizable evolution: state-of-play audit of the existing engine by an agent team first, then evolve the audited modules — never restart from zero, never overwrite working machinery.

Any change that violates one of these standing principles is wrong even if every gate stays green:

- **P1 — No fakery.** Every safety/traceability/coverage/progress mechanism must be genuinely verified and enforced by the orchestrator. A report, matrix, or hash that nothing downstream checks is forbidden. Deterministic wherever possible.
- **P2 — Zero humans in the development loop.** Exactly one legitimate human touchpoint exists: the owner decision on a Change Request. Retry buttons are human interventions *on* the machine, never steps the machine waits for. Every operational input the loop needs is machine-established, never hand-edited — the verification gate command included (see the dev-loop invariant below).
- **P3/P4 — Loud failures, no blind states.** On any detected problem the orchestrator remediates automatically within bounded attempts, then blocks loudly (report + notification). Being silent about what happened, where, or why is forbidden; the loop always progresses or surfaces a block.
- **P5 — Flexibility inside determinism.** Judgment lives in agent legs at decision points (readiness verdicts, proof verdicts); the orchestration around them stays deterministic and evidence-based. Enforcement of rules is always the orchestrator's, never the agent's.
- **P6 — ShadcnUI only.** All UI comes from shadcn primitives and tokens; nothing hand-invented in raw Tailwind.
- **P7 — Non-loop / dev-loop boundary.** Left of the boundary (spec intake: import, Vivi) there is no automatism — only user ↔ Vivi. Right of it, everything is autonomous. UI must preserve and display this boundary.
- **P8 — Stage typing.** Every workflow stage is typed deterministic / agent / mixed (`components/workflow/workflow-stages.ts`); a new stage declares its type and the UI shows it.
- **P9 — A notification exists only if it pushes the owner to DO something.** Write one iff it asks for an owner action (decide a CR, fix a red gate or a refused write, retry, unblock) or announces a state they are waiting on from outside the app (the run finished, the run halted). Never write one whose honest summary is "everything worked, nothing to do" — housekeeping, a phase progressing normally, a selection, a successful self-heal, a receipt for a click the owner just made: the durable record is the commit, the report and the progress ledger, and the live state is the status badge. So every notification is `warning`/`error`, which is what arms the Ask-Vivi pill (`isActionableNotification`, `components/chat/vivi-notifications.tsx`), with `run_finished` the ONE sanctioned `success`. Keep a failure only where it too demands an action; a failure the owner can do nothing about is as silent as a success.
- **P10 — No useless work.** The canonical never chases the code; doc updates happen only when intention changes.

**Atomic verified increments — the step size is bounded everywhere the method produces steps.** Every unit of work the workflow emits — an extracted issue, a per-issue green-gate commit, a proposed CR or feature cycle — is the SMALLEST slice that still proves one behavior end to end, added without ever leaving the system broken between steps (the orchestrator commits only on a green gate, and each increment must pass its own gate alone). DECOMPOSE a spec area or an owner ask too big for one slice into an ordered chain of gate-provable slices BEFORE implementation; never land it as one sprawling change. The floor is end to end: a slice too thin to prove a behavior on its own is wrong too. This bar has five live copies that must move together with it — `factory/prompts/extractor.md` (granularity law), `factory/prompts/extraction-verifier.md` (granularity finding), `factory/prompts/reviewer.md` (proportionality signal), `factory/prompts/vivi.md` (slice a big ask) and the managed method block in `factory/templates/AGENTS.md`, which is what carries it into every governed repo.

**Document preparation is the FIRST workflow stage.** Import is dumb-fast acquisition (raw files → `.vivicy/uploads/<batch-id>/`, never touched again); document preparation (`factory/prepare-docs.ts`) turns that raw batch into the canonical corpus, so it runs a posteriori (the owner starts the workflow; never at import) and BEFORE extraction — hosted at the head of the extraction orchestrator, staleness-gated, since prep's outputs must exist before `doc-baseline` freezes them. **Batch↔cycle law.** A batch is bound at IMPORT to the cycle then active: the active cycle id while the canonical is pre-freeze (the project cycle before the first freeze, else the open feature cycle), or a next-cycle SEED marker while the canonical is frozen — a post-freeze import feeds the NEXT cycle, never the frozen corpus. Prep consumes ALL unconsumed COMPLETE batches of the active cycle in one run: `manifest.json` is the completeness marker, a manifest-less batch is an interrupted write and is skipped, a seed batch becomes unconsumed-active the moment its cycle opens, and a batch bound to another cycle is never consumed by this one. Mark a batch consumed only after all its files land, so a crash mid-prep can never claim an unconsumed batch. Per file, a deterministic router routes and an agent leg judges (P5): a file already under a canonical target location with a valid extension and in the dominant language is placed untouched-in-content; everything else — messy docs (docx/pdf/rtf/odt text-extracted deterministically first) and any canonical-located doc in a non-dominant language — goes to the leg, which explodes/translates into canonical form while the orchestrator validates its scratch output and places it (the leg writes nothing into the governed tree, W2). **Language law:** one language governs a cycle — the project's already-established canonical language, or, greenfield, the first batch of the run fixes it; every prepared output is in it and a divergent later batch is TRANSLATED toward it; uploads are never modified; there is no warning and no human language arbitration. **Prepare, don't judge:** classify, place, explode, translate — drift/contradiction/coherence analysis stays downstream.

**Shared-file law.** Scaffolding a governed repo sorts every root file into three classes with three write rules (`lib/scaffold.ts`, engine in `lib/managed-block.ts`): owner files (`README.md`) are written only if missing and never edited (`writeIfMissing`, "point final"); machine files (`vivicy.json`, `.vivicy/**`) are created-then-owned; shared governance files (`AGENTS.md`, `CLAUDE.md`, `.gitignore`) carry exactly one Vivicy-managed block between begin/end markers (`<!-- vivicy:method:begin/end -->` for the Markdown pair, `# --- vivicy managed block … ---` for `.gitignore`) whose canonical content is single-sourced by extracting it from the greenfield template. Four shapes and no fifth: absent → the full greenfield template (which embeds the block, so re-governance is a fixpoint); present without markers → the block is appended at EOF (one blank-line separator, clean trailing newline); present with exactly one well-formed marker pair → the block is re-normalized in place, everything OUTSIDE the markers staying byte-identical to the owner's bytes and only exact full-line marker matches counting, so owner text that merely resembles a marker survives; markers damaged in any way (duplicated, unterminated, stray, misordered) → the residue is cleaned and one pristine block is put back. Re-apply all four at every project OPEN (`renormalizeManagedFiles`, called by `POST /api/project` right after the selection is persisted), not only at acquisition, and keep BOTH doors onto that seam alive — the picker's explicit selection, and app boot re-firing the very same POST for the already-persisted governed project (`hooks/use-reopen-persisted-project.ts`) — or a returning session, which resolves its project by GET and never clicks, never receives a block-definition evolution. The set of managed files is single-sourced in `lib/managed-block.ts` (`MANAGED_GOVERNANCE_FILES`, derived from the `MANAGED_MARKDOWN_FILES` pair every Markdown-block writer shares), which `factory/dev-loop.ts` and `factory/install-skills.ts` import by raw relative path with no bundler while the app imports it through `@/`: that module must stay a LEAF — no Next alias and no relative value import, since none satisfies both TypeScript programs — and server-only, the atomic writer living there. Open renormalizes the three SHARED files and nothing else: greenfield-only artifacts (`README.md`, `vivicy.json`, `.env.example`, the skeleton dirs) are never re-run, the seam issues NO git command, and neither half of it may fail the open — it collects per-file failures instead of throwing (the owner is told which file and why, P3/P4), and the route calls it for its effect inside its own guard AFTER the selection is persisted. A healthy project and a real refresh alike must be a zero-write, zero-notification no-op: only a file Vivicy could NOT update reaches the owner (P9). The dirty tree a real refresh leaves is the DEV LOOP's to absorb, never the owner's to explain: `ensureCleanTreeForRun` (`factory/dev-loop.ts`) commits it as one `chore:` commit before its clean-tree gate, but ONLY when the dirty set is exactly managed governance files and with an exact pathspec, so a concurrent owner edit cannot be swallowed; any other dirt still reaches the owner's verbatim dirty-tree refusal. `ensureManagedBlock` is TOTAL — it never throws. Vivicy owns a span only when its begin and end are each other's NEAREST counterpart (an end pairs with the closest begin above it, never across an intervening begin) plus any marker LINE left unpaired; every other byte is the owner's, preserved verbatim and never reordered, and ambiguity always resolves owner-side. **The write itself is byte-level and atomic** (`writeManaged`, the single seam every managed-block writer reaches — the scaffold's two, and the skills stage): markers and block are ASCII, so locate/splice and the equality short-circuit run over the owner's RAW bytes and any ASCII-compatible encoding — latin-1, UTF-8, a UTF-8 BOM — comes back byte-identical outside the span; a UTF-16/32 file (BOM-sniffed) is refused untouched, as a typed `ManagedWriteError` carrying the owner-facing reason (`managedWriteFailureReason`, the one place Node's `, <syscall> '<path>'` tail is trimmed), through the channels that already exist (a collected failure at open, a `ScaffoldError` at governance start, a red skills stage), never mangled. Write the new bytes to a temp BESIDE the resolved target (the `readlink` chain, so an owner's symlinked `CLAUDE.md -> AGENTS.md` keeps its link and its target receives the block, and the rename never crosses a filesystem), created EXCLUSIVELY over a removed stale temp (a killed run's leftover must never be opened: a symlink there would capture the write, and a reused inode would carry its mode into the owner's file), carry the target's exact mode by applying it to the open fd AFTER the write since the umask masks a create mode, then `fsync` and publish with one `rename` — data before name. `MANAGED_GOVERNANCE_FILES` therefore lists `.gitignore` FIRST: it carries the never-commit rules, so writing it last would leave every other managed file's temp uncovered on the very pass that installs the block. Because a rename ignores the target's own mode, refuse a read-only file — and a read-only DIRECTORY — explicitly rather than write through it. Never trade the rename's atomicity to preserve a hard-linked second name (it keeps the old content) or file ownership (it becomes the process's); a link the owner points OUT of the governed root likewise takes its temp with it, into a directory whose ignore rules are not Vivicy's to write. The `.gitignore` block's content is the never-commit set every Vivicy commit depends on being exhaustive — an ignored path is invisible to the `git status` each commit's pathspec is read from — the factory runtime, per-issue worktrees, integration lock, transcripts, proof artifacts, the atomic-write temp above, and the secret-bearing dotenv/direnv family (`.env`, `.env.*`, `.envrc` — direnv matches neither of the others), since the loop stages and pushes at every checkpoint. The block carries EXCLUDES only, with the proofs `recipe.txt` as the single deliberate exception: it is appended at EOF, so a `!` re-include inside it would override an owner rule above it and put a file they chose to hide back in reach of the loop's commits. Exclude the env family in EVERY shape and re-include it NOWHERE — not even in the greenfield catalogue below the block, since the first marker repair re-appends the block at EOF UNDERNEATH that line and flips the placeholder to ignored permanently. Greenfield instead ships a REAL `.env.example` (write-if-missing, greenfield-only — an owner's existing tree never receives a file they did not ask for) and force-adds it: into the initial commit where Vivicy inits the repo itself, and into the owner's own index where they had already init'd the target for this project (staging only — no commit and no identity Vivicy does not otherwise create). Git never ignores a path that is in the index, so a TRACKED file is immune to whatever the ignore rules later become. Write that placeholder ONLY where the delivery is possible — a target that merely sits under a FOREIGN parent repo gets none, staging into an index Vivicy does not own breaking the sacred-state law: Vivicy writes nothing it cannot deliver. Generalist hygiene (`.DS_Store`, logs, editor dirs) is opinion, stays greenfield-only, and never enters the block. The method block is orthogonal to the `<!-- vivicy:skills:begin/end -->` block the skills stage maintains at the tail of the same two documents: each is owned by its own writer and one pass may only ever touch its own span, but both ride this ONE engine — never write a second byte-splice, a second encoding sniff or a second temp-and-rename.

**Cycle concurrency (project cycle singular forever; feature cycles designed-for-parallel, gated one-active).** A repo has exactly ONE project cycle — its pre-freeze life, the greenfield build — never opened, never parallel to anything, closed only when the first freeze snapshots it. FEATURE cycles are designed for parallelism (each drives its own issue implementation worktrees) but exactly one may be open at a time. Keep both rules one law, single-sourced in `lib/spec-cycle.ts#featureCycleOpenRefusal` — the only gate `lib/control.ts#openSpecCycle` and `factory/cli.ts` cycle-open open a cycle through, so the policy can never drift between app and CLI: `no_frozen_baseline` refuses opening a feature cycle while the project cycle is still live, `feature_cycle_active` refuses a second concurrent feature cycle, both as a typed machine-facing refusal (`ControlError "cycle_state"` / CLI `EXIT_REFUSAL`, HTTP 422), never a crash.

## Truth model (why CRs exist, and when direct edits are legal)

One source of truth per type of truth: product intention = canonical spec + accepted CRs; work to do = issues; real result = code + tests; conformity proof = gates + traceability. Issues and code are never the product truth. The current product contract = the latest frozen canonical baseline + accepted CRs not yet folded in; an accepted CR must eventually be folded into the canonical (never an old spec plus infinite annexes).

**Spec kinds and cycles.** A governed project's life is an ordered chain of spec CYCLES: at most one **project** spec (greenfield — the repo carries no product code when the spec starts) then any number of **feature** specs (evolutions of the existing codebase), one active at a time. The kind is detected MECHANICALLY (`lib/spec-kind.ts`, tracked files outside `.vivicy/` and the scaffold surface) and stamped into the frozen baseline manifest (`spec_kind`) — never an agent's judgment. Between two builds, opening a feature cycle (`lib/spec-cycle.ts`, the `.vivicy/development/reports/spec-cycle.json` state file) is the official mechanism for evolving the canonical: it reopens Vivi's pre-freeze allowlist, the supervised build is refused while it is open, and the NEXT extraction freeze (a MINOR version bump, `approval_ref` = the cycle id) closes it mechanically — a cycle is never closed by declaration. Mid-build intention changes remain CRs (rule 3 below); post-delivery feedback triages into CRs (conformity) or the next feature cycle (new intention). Cancelling a cycle is legal only while the canonical still verifies against the frozen baseline.

The four routing rules, all enforced in code (`lib/vivi.ts` allowlists, `factory/change-control.ts`, `factory/cr-apply.ts`, the readiness leg):

1. Ambiguity found during extraction (pre-build): fix the spec directly, re-freeze, re-extract — no CR.
2. A spike discovers a real constraint post-freeze: CR mandatory — the spike proposes, never edits the spec (pre-freeze spike proving may edit directly).
3. The need changes during development: CR mandatory — the official mechanism for "the initial intention is no longer right".
4. An issue becomes non-implementable because of already-produced code: execution-plan problem → modify the issue only; intention problem → CR toward the spec. A CR whose application touches the canonical always forces a re-freeze.

## Per-leg timeouts (agent legs cannot hang the loop)

Every agent leg (both the dev-loop's implementer/reviewer and the extractor/verifier) runs through the shared spawn infra (`factory/agent-spawn.ts` → `factory/leg-timeout.ts` → `factory/leg-supervisor.ts`) under TWO independent watchdogs, so a wedged `codex exec`/`claude` (alive but producing nothing) can never block the orchestrator:

- a **hard wall-clock cap** (`VIVICY_LEG_TIMEOUT_MS`, default 45 min) — the absolute ceiling for one leg, sized above a legitimate xhigh-effort leg;
- a **stall/idle timeout** (`VIVICY_LEG_IDLE_MS`, default 12 min) — no new stdout/stderr for this long means the CLI is wedged even before the cap.

Whichever trips first kills the leg's **whole process group** (SIGTERM, then SIGKILL after `VIVICY_LEG_KILL_GRACE_MS`, default 10 s — never the pid alone, the CLI spawns children) and returns a structured timeout failure (`timedOut: true`, a human reason, a non-zero status). Treat a timed-out leg as a FAILED attempt inside the existing bounded retries (retry the issue; if it keeps timing out, record `issue_blocked` / `extraction_blocked` naming the timeout — never hang). Set any of the env values to `0` to disable that watchdog. The verification gate (the target's `vivicy.json` `gateCommand`) is NOT an agent leg and is not subject to this policy.

## Public-API quality bar (where it lives, and why no dead-code gate)

The deterministic gates prove coverage, traceability, and that the project's own test command exits 0 — never the quality of a public API. Put that bar in the **role prompts**, never in a new deterministic check: the implementer's "QUALITY BAR" (`factory/prompts/implementer.md`), the reviewer's matching MUST-fail checklist (`factory/prompts/reviewer.md`), and the fidelity verifier's cross-document consistency check (`factory/prompts/extraction-verifier.md`), which reconciles a spec describing one data shape two ways BEFORE implementation. `factory/dev-loop.test.ts` locks those prompt invariants.

**Never add a deterministic dead-export gate.** Vivicy is language- and project-agnostic, and a robust detector needs per-language call-graph reachability from declared entry points plus a declared public-API surface; without those, a "referenced only inside its own module + tests" heuristic flags every legitimate public-library export and misses the real signal ("not on the production path"). The reviewer checklist owns this instead.

## Test matrix (mandatory upkeep)

`test/TEST-MATRIX.md` (committed) is the exhaustive inventory of every test case — covered and GAP — for the whole system, organized by area plus cross-matrices. **Every change that adds, changes, or removes behavior MUST update the matrix in the same working session**: add new cases at the next free id in the right area, update the scenario/expected text of changed ones, delete cases for removed behavior (ids retire, never get reused), flip `GAP` to the covering test reference when you write one, and adjust the status table counts for the touched areas. Case ids are stable: never renumbered, never reused.

This mandate is machine-verified (P1): the matrix header carries a `Reconciled fingerprint:` over the behavior-bearing source tree plus the HEAD commit hash at reconciliation, and `scripts/test-matrix.test.ts` (in the vitest suite, so `npm test` runs it) fails when the code changed without a re-stamp, when the status-table counts drift from the actual bullets/GAPs, or when case ids collide. After reconciling the matrix — including after a pure no-behavior refactor — run `npm run matrix:stamp`.

The reconciliation itself is agent work with a git-derived work-list: `npm run matrix:delta` prints exactly the behavior files changed since the stamped commit — read those files, reconcile their cases, recount, stamp. Stamping without doing that reading is falsifying the declaration; never do it.

Repo skills live under `.agents/skills/` (committed, standard SKILL.md format). Every agent must follow them when their trigger applies; this list is their registry:

- **matrix-reconcile** ([.agents/skills/matrix-reconcile/SKILL.md](./.agents/skills/matrix-reconcile/SKILL.md)) — reconcile `test/TEST-MATRIX.md` from the git delta; trigger: the matrix guard is red, a behavior change is about to be committed, or the matrix is being updated for any reason.

## The golden rule — every artifact earns its keep by driving behavior

Everything this repo carries — every doc, prompt, directive, comment, and line of code — must drive what an agent or a human DOES; content that only reassures rots into a stale lie, so delete it rather than write it. This never deletes a contract: a quality bar, a security boundary, or a cross-process invariant CHANGES behavior and is kept, even hardened. And the rule bounds WRITING, never observation: be exhaustive in reading, search, and verification — token economy never trumps evidence, a partial observation is a false observation — and minimal only in what you add.

**Zero comments by default.** A comment may exist ONLY when it states a structural invariant, constraint, or danger that is **not derivable from the code itself** — the "this breaks if you change it" class: a cross-process byte-compatibility contract, a deliberately non-obvious ordering, a platform trap, a security boundary. One dense line, no story. The canonical set of such invariants lives in the "Structural invariants" section below — prefer pointing there over repeating them inline. Never write: narration or paraphrase of the next line, JSDoc/docstrings that restate names and types, module-header essays, decorative banners. Tool directives (`eslint-disable`, `@ts-expect-error`, `"use client"`, shebangs) are not comments — keep them. When editing a file that still carries non-invariant comments, delete them as you pass.

**No backward compatibility before the first public release.** Nothing on disk predates the current code, so a contract change is made CLEAN — one format, one reader, one writer — with every fixture re-frozen onto it and the dead shape refused where a validator exists, never tolerated by a dual-format reader, a renamed-key alias, a default-backfill, or a migration shim. A mechanism that serves the FUTURE product (managed-block renormalization, error-tolerant parsing of user- or agent-authored input, degradation on a file that never had another spelling) is not compatibility and stays.

**Never encode a moment in time.** Do not encode version markers, plan/workstream/sprint/phase codes, "new/old/legacy/added in vX" wording, or session references in identifiers, strings, file names, comments, or docs. Version data a machine reads is functional, not a marker (dependency manifests, protocol/schema version fields, the semver in `package.json`) — it stays.

`npm run lint` enforces this mechanically: a custom rule (`scripts/eslint-comment-density.ts`, wired in `eslint.config.mjs`) caps per-file comment density across the whole repo, `factory/` included. It caps QUANTITY only — never add a lexical narration check beside it: comment CONTENT is judged by the agent reading the diff, for the same reason there is no dead-export gate.

## Structural invariants (the non-derivable "why"s — the only sanctioned comment content)

**Commit pathspecs (the universal law: the factory never blind-commits)**
- `lib/pathspec-commit.ts` (`commitDirty`, `dirtyPaths`) and every commit site in `factory/` and `lib/` – never `git add -A`, `git add .`, or a pathspec-less `git commit` anywhere in the product: a commit stages an explicitly enumerated path set and rides exactly that set (`--pathspec-from-file=- --pathspec-file-nul` on the add AND `--only` on the commit, so neither the tree nor the index can smuggle anything in). Foreign state — an ecosystem install dir, a `.venv`, an owner's draft — is then excluded by CONSTRUCTION instead of by whatever the target's ignore rules happen to cover, which is the only guarantee that holds in every language. The set is the writer's DECLARED territory narrowed to what git observes dirty inside it at ONE instant (`status -z --untracked-files=all`: an untracked directory is one entry `git add` would re-glob, and any filename is legal), minus what was already dirty when the writer took the tree. Territories: `.vivicy` (+ `vivicy.json`) for the extraction corpus and CR-apply, `VIVICY_SCAFFOLD_PATHS` for the pre-freeze snapshot (the scaffold's own root files included, since the freeze refuses a dirty tree and `.env.example` is staged-not-committed by design), the causal record for the skills stage, and for the scaffold's own first commit the file list it just wrote. The pre-freeze snapshot is the ONE place a whole-tree pathspec is legal, and only when the target has no commit at all — the owner pointed Vivicy at a folder of their files, `ensureGitRepo` init'd the repo around them, and that first commit has no history to swallow, bounded by the ignore catalogue the scaffold wrote; a target that already has history gets the footprint alone. The per-issue checkpoint snapshots the tree's foreign dirt ONCE, when the issue takes the tree (`snapshotPreIssueDirt`, dev-loop), never per attempt: a file attempt 1 wrote and attempt 2 left alone would drop out of the checkpoint. A path staged as DELETED, and a rename's origin, are skipped on the add and kept in the commit — `git add` on a path in neither index nor worktree fatals and aborts the whole staging. Whatever a stage does not carry is named on stderr where it happened: the freeze and the dev loop both refuse a dirty tree, and a path left behind is the owner's to commit, never Vivicy's to swallow.

**CLI ↔ app parity**
- `factory/cli.ts`, `lib/control.ts` – never import each other; parity holds only because both spawn the identical factory scripts/args and read/write the same state-file schemas (`run-state.json`, `skills-install.lock`, `doc-prep.lock`, `notifications.jsonl`, `current-project.json`), never shared code beyond the dual-program LEAVES below that own a path or a lock protocol outright (`lib/project-runtime.ts`, `lib/stage-lock.ts`).
- `lib/project-runtime.ts` – single derivation of project-scoped runtime/lock paths, imported identically by the Next app and by `factory/cli.ts` via a raw relative import with no bundler, so it must stay free of `@/` aliases and Next-only imports; this is what makes a CLI-started and a UI-started run agree on one lock.
- `lib/control.ts` (`claimRunLock`), `factory/cli.ts` (`claimCliLock`) – every lock a CLIENT owns is claimed with the fs `wx` exclusive-create flag before spawning, never written unconditionally, closing the check-then-spawn TOCTOU window both clients depend on.
- `lib/stage-lock.ts` (`claimStageLock`, `stageLockHolder`), `factory/install-skills.ts` (`openStageTree`, `settleStageTree`), `lib/control.ts` (`refuseWhileSkillsStageHolds`), `factory/cli.ts` (`skillsStageInFlight`) – the skills stage claims `skills-install.lock` ITSELF, inside the process that does the writing, so the supervisor's own child, the app's detached spawn, the CLI and Vivi all inherit ONE refusal instead of each claiming for itself: the claim rides `openStageTree` and is released by `settleStageTree`, the same `finally` that closes the absorption on the return AND the throw path. Clients only PROBE that one file — read-only, with their own liveness source injected — and refuse fast with the typed `already_running` (HTTP 409, `EXIT_REFUSAL`) the routes already map; a dead heat between two spawns is decided by the child's exclusive create. A caller-side claim would be wrong here and not for the run lock: a DETACHED caller cannot release what it claimed. Breaking a lock whose recorded holder is gone is IDENTITY-guarded and never frees the path to establish that identity: hard-link the residue aside under a per-process name FIRST, require the LINKED bytes to be the residue that was inspected, and unlink the lock path LAST, gated on two re-proofs taken immediately before it — the `.break` marker still names THIS process, and the lock path is still the very entry that was linked. Never move the file away to inspect it; those two re-proofs are where the containment lives, and the window they leave (two simultaneous one-syscall stalls in two processes) is carried as a measured residual (`cli-supervisor-process-infra.557`) rather than closed, POSIX offering no compare-and-swap on a path. PUBLISH the marker atomically — bytes to a per-process temp, then `link`ed into place, never an exclusive create, which is an open plus a write whose interruption leaves a PARTIAL marker reading as owned by nobody. Refuse an UNPARSEABLE marker as a foreign artifact, never take it over; take over a marker whose recorded owner is GONE under the SAME link-aside / re-proof-owner-and-entry / unlink-last discipline, and let a taker that REFUSES destroy NOTHING. Mark every per-process name a killed break can leave — the aside link, the marker's publish temp, its takeover name — with the pid IN the name, never with the sweeper's position, and sweep them (an unparseable marker included) from whichever process ends up HOLDING, janitorially, in a way that can never fail the claim it just won. A lock that exists but cannot be READ is residue too, broken on the aside link's inode alone rather than dead-ending the stage; a lock path that is a DANGLING symlink is REFUSED instead — `link(2)` follows symlinks here, so no identity can be pinned, and removing an entry on sight is exactly how a live claim gets destroyed. `release` removes the file only while it still carries its own pid.

Two prompt contracts and no third: `legDepsForTarget` appends the stage's per-run context AFTER the composed role prompt (composing the concatenation instead would substitute inside agent-written context — a CR body, prior-attempt feedback — which is quoted evidence, never a template), `legDepsForVerbatimPrompt` sends a prompt `lib/vivi.ts` already assembled whole and discards the role template (still read, so an unknown or empty role is still refused). **Platform traps & security boundaries**
- repo-wide – any code deriving a stable key or doing path comparison from a path under the OS temp dir or a persisted target root (runtime-key hashing, e2e fixtures, test assertions) must `realpathSync` it first: macOS symlinks `/tmp` to `/private/tmp` (and `/var` to `/private/var`), so an unresolved path forks state/locks across two spellings of the same directory.
- every GIT ignore carrier (this repo's `.gitignore`, the greenfield catalogue in `lib/scaffold.ts`, the rehearsal fixtures) – `node_modules` is written WITHOUT a trailing slash: the slash restricts the match to directories, and the workspace/container/worktree layouts that LINK it to an install elsewhere would otherwise be untracked-and-committable at every checkpoint the loop commits. It stays greenfield-catalogue content and never enters the managed block, which carries Vivicy's own artifacts and the secret family, not one ecosystem's hygiene (`.DS_Store` is the settled precedent). `.prettierignore` deliberately keeps its slash and needs no such rule — prettier's globber never descends a symlinked directory — but that is an upstream default, so it is PINNED (`scripts/nested-checkout-ignores.test.ts`) rather than assumed; the same file pins the git side against the repo's own `.gitignore` bytes. A test that spawns git to assert an ABSENCE — nothing tracked, tree clean, path ignored — MUST redirect `HOME` and `XDG_CONFIG_HOME` to an empty dir on top of `GIT_CONFIG_GLOBAL`/`GIT_CONFIG_SYSTEM`/`GIT_CONFIG_NOSYSTEM`: git reads its default per-user excludes (`$XDG_CONFIG_HOME/git/ignore`, else `$HOME/.config/git/ignore`) whether or not `core.excludesFile` is set, and a per-user rule can only ADD ignores, so it can only ever turn such an assertion green. Presence assertions need nothing — an extra ignore can only make them red. Each such test file owns ONE git seam that applies the redirection; never open a second, and route every read that DECIDES an assertion through that seam's exit-status guard — a git that could not observe the tree hands back the same empty stdout a clean one does.
- `factory/cleanup-tree.ts` – removing a directory tree a just-finished child may still be flushing into must never lean on `fs.rm`'s `maxRetries`/`retryDelay` — the racing entries spend that budget during the walk (measured: ENOTEMPTY whatever the budget), so convergence needs the WHOLE recursive removal re-invoked after a wait. `cleanupTree` is that one guard: it never throws (a cleanup that raised would replace its caller's outcome) and it announces through `writeSync(2, …)`, `process.stderr` being async on a pipe and dropping what an exit handler writes.
- `scripts/clean-artifacts.ts`, `tsconfig.json`, `factory/tsconfig.json` – the wrapper is plain-node tooling that imports the factory primitive with a runtime-exact `.ts` specifier, which the app program rejects (TS5097) and which would drag `factory/` into the Next TypeScript program the app config excludes on purpose; it is therefore excluded from the app `tsconfig.json` and type-checked by `factory/tsconfig.json`, whose include already covers `../scripts/**/*.ts`. `tsconfig.json` must also stay strict JSON (no JSONC comments): this same wrapper `JSON.parse`s it to prune stale dist includes, and its parse failure is silently swallowed.
- repo-wide tool configs (`eslint.config.mjs`, `vitest.config.ts`, `playwright.config.ts`, `scripts/test-matrix.ts`) – every tool that DISCOVERS files by walking this tree must be blind to the nested checkouts a machine holds (`.claude/**` local tool worktrees, `.vivicy-worktrees/**` dev-loop worktrees), or the gate goes red-by-environment on phantom copies of files nobody edited: ESLint alone needs explicit `globalIgnores` patterns since it neither skips dot-prefixed segments (tsc does) nor reads `.gitignore` (prettier does — which makes the `.gitignore` entries for both dirs load-bearing for `npm run format`), vitest carries its own `exclude`, and Playwright's `testDir` plus the matrix walker's `BEHAVIOR_DIRS` are root-anchored allowlists that need nothing; `scripts/nested-checkout-ignores.test.ts` pins both opt-in ignore sets (ESLint's and vitest's), prettier's `.gitignore` reading — an upstream default, load-bearing because `format:check` is a gate — and the walker's blindness.
- `app/globals.css` (`@source not "../**/*.{test,spec}.{ts,tsx}"`) – Tailwind's automatic source detection scans the repo's PROSE, not just `.ts`/`.tsx`: a utility class named once in a markdown file compiles into the shipped stylesheet (measured), and that exclusion covers test CODE only. So no doc, README or matrix row may spell a live utility class name — quoting one ships dead CSS nobody renders, and quoting the witness class of `app/globals.test.ts` reds the very invariant that test exists to hold.
- `.prettierrc` (`prettier-plugin-tailwindcss`, `tailwindFunctions: [cn, cva]`) – the formatter REWRITES class-list string CONTENT: it sorts each class string into tailwind's canonical order and trims it, so a class name whose separating space lives inside a template-literal interpolation (`` `a${on ? " b" : ""}` ``) loses that space and silently concatenates into `ab`. Compose conditional classes with `cn("a", on && "b")` — one class per argument, no separator left for the sorter to eat. The same rewrite is why the one assertion that feeds a deliberately non-canonical class order carries `// prettier-ignore` (`lib/utils.test.ts`): only `cn`/`cva` CALLS are tailwind functions, so without the fence the pass sorts the assertion's INPUT and leaves its expectation untouched, reddening the case.
- repo-wide UI components – interactive controls that must stay focusable while conceptually disabled/busy/locked (composer, send button, decision-card buttons, Radix `AlertDialogTrigger`, the one-shot Extract button) use `aria-disabled` plus a guarded no-op handler, never the native `disabled` attribute, which drops keyboard focus to `<body>` or breaks Radix's return-focus-to-trigger on close.
- `components/chat/vivi-panel.tsx` – the panel is `w-[min(100%,clamp(380px,25vw,480px))]`, never the bare clamp: the 380px floor alone exceeds every small-phone viewport (320–375; from 390 up the clamp already fits), and a `fixed` box never joins the document's scrollable overflow, so the excess is clipped off-screen unreachably and NO page-level overflow probe can see it; `100%` and not `100vw` because a fixed box resolves percentages against the viewport minus a classic scrollbar. `e2e/overflow.spec.ts` therefore measures the panel's own geometry, and bounds each descendant by the nearest ancestor that clips WITHOUT scrolling (overflow hidden/clip, or the paint containment `content-visibility` implies) — a scroller ancestor is no bound, its content being one swipe away.
- `components/chat/menu-card.tsx` – the sanctioned rounded CARD: an in-chat card is a physical object lying in the transcript, so it alone departs from the square shadcn card primitives (`rounded-none` on Card/Button/Input/Badge/Textarea); the rounded chrome elsewhere in the chat and the sidebar is a different class and is untouched, and a new chat CARD composes this base rather than inventing a rounded variant of its own — the paper/frame/turn styling has no second home. Both faces stack in ONE grid cell, so a card is one box as tall as its tallest face at every instant; never swap which face is in flow, that clips the side still facing the viewer (the transcript row is paint-contained, `components/ui/message-scroller.tsx` `[content-visibility:auto]`) and reflows the thread mid-turn. Everything a card PAINTS stays inside that same box: a face's hairline ring and its drop shadow both fall OUTSIDE the face's own box, so the card's ROOT reserves room for them at its outer edge, composed last so no consumer's padding can spend it — and the turn is ORTHOGRAPHIC, with no perspective anywhere on the card, since under one the half rotating toward the viewer is projected larger and the box grows vertically mid-flip past any room a card could hold. A card turns to its back face only when the decision spends every action its front offered (the import card); one whose locked buttons remain the transcript's record of the question (CR cards) keeps its front, per the `aria-disabled` rule above. The face is derived from state and the turn is armed only for the false→true transition a mounted instance witnesses, so a rehydrated transcript can never replay it, and the turn moves focus to the back face — inerting the spent side would drop it to `<body>`. `MenuCardPile` extends the same physics to a STACK: the sheets behind the live card are paper, never content (`aria-hidden`, no text), and their resting offset+rotation is static geometry kept strictly INSIDE the pile's own padding, since that same paint containment shaves any rotated corner reaching past the row. That padding is the COMPLEMENT of the room the live card already reserves, never a second copy of it — a sheet's absolute inset is measured from the pile's outer edge and reaches past any padding, and the two together are what hold the sheets' peek constant — and its horizontal half stays constant across the pile's whole life so the live card never changes width as the pile shrinks.

Cross-request server state therefore lives in a process-global registry (`globalThis` under a `Symbol.for` key — shared by every evaluation, gone when the process is) or on disk, never in a module `let`, whatever the bundler in play.
- `components/ui/sonner.tsx` – the toast stack is centred on the map CANVAS, not the viewport: it is shifted by half the live rail width (`usePanelState`, the same source the layout uses — 0 while the rail is undocked) and capped to the canvas minus a gutter, because the rail carries the process control bar (status badge, Run/Stop, Extract) and a stack that reaches it hides the state it announces and swallows the owner's next click for the whole toast duration. Keep the scan linear by treating a FAILED closing-line search as terminal (no ``` line at or after that offset means no later occurrence of the tag can close either, each opening over a suffix of the same range); never rescan the tail per occurrence, which is quadratic on the ordinary markdown shape of the tag repeated mid-line. `lib/fenced-block.test.ts` pins all three hostile shapes at 200 000 characters, the multi-open one under a budget that separates linear from quadratic by an order of magnitude in both directions.

## Writing prose, and the formatter that keeps code honest

Markdown and prose use **natural** line breaks: one line per paragraph. Never hard-wrap prose to a fixed column — a line break is semantic (a new paragraph or list item), not cosmetic. List items stay one item per line; tables, fenced code, and intentional hard breaks are preserved as authored. Editors and Prettier must not re-wrap prose (`proseWrap: preserve`).

Code obeys the same law, enforced instead of trusted. `npm run format` and `npm run format:check` share the one `.prettierrc` over `**/*.{ts,tsx}`, and `npm run lint` runs the check through `postlint` — so a format-dirty tree reds a gate every landing already runs, while `npm run lint -- <file>` still lints exactly that file (the hook is what keeps the format half repo-wide). Every option in `.prettierrc` is the authored MAJORITY (measured across the whole tree): flipping any of `semi`, `singleQuote`, `trailingComma`, `bracketSpacing`, `arrowParens`, `quoteProps`, `objectWrap` or `bracketSameLine` away from what is written there dirties more files, not fewer. `printWidth` is the only option with a real trade-off — too low it folds natural-length lines into a column, too high it joins deliberately multi-line structures into monsters no human reads — so it is a measured optimum, not a preference: re-measure churn and the tree's line-length distribution before touching it, never argue it.
