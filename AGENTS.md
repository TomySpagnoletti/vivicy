# Vivicy — agent guide

Vivicy is a visual autonomous dev factory — a **web app**. See [README](./README.md) for what it is and how to run it. This package has two parts:

- `factory/` — standalone Node ESM tooling. The actual modules: the issue extractor (`extract-issues.ts`), the dev-loop orchestrator (`dev-loop.ts`) and resumable supervisor (`dev-loop-supervised.ts`), the status probe (`dev-status.ts`), the rehearsal harness (`dev-rehearsal.ts`), the per-issue progress ledger (`progress-ledger.ts` — the single source of truth for progress, written mechanically by the orchestrator), the polyglot gate config (`project-config.ts`, reading the target's `vivicy.json`), the agent-leg spawn + per-leg timeout infra (`agent-spawn.ts`, `leg-timeout.ts`, `leg-supervisor.ts`), the documentation-baseline lock (`doc-baseline.ts`), the semantic-extraction and traceability gates (`semantic-extraction-check.ts`, `traceability-check.ts`), the agent prompts (`prompts/` — one file per leg role), the lean-target scaffold templates (`templates/`), and the architecture-map viewer-data generator (`generate-viewer-data.ts`). Plain `node`, no Next coupling. It has its own `factory/tsconfig.json` and a Node `--test` suite; it is excluded from the Next app's TypeScript and ESLint configs on purpose. There is **no progress MCP and no lifecycle-hook seam** — agents never report progress; the orchestrator owns the ledger.
- `app/`, `components/`, `lib/` — the Next.js App Router control plane that drives the factory and renders the architecture map. The map data is a static graph generated once at extraction; `app/api/map/route.ts` overlays the live ledger (`lib/development-overlay.ts`, `lib/map-data.ts`) at read time, so the loop never regenerates the map per issue.

The factory operates on a **target project**. The app resolves it in order: the project the user picked in the UI (persisted in the runtime dir) → the `VIVICY_TARGET_ROOT` env var → the parent of the process cwd (`..`). Vivicy is standalone, not vendored into the target. Never hardcode machine-specific paths.

Gates: `npm run typecheck`, `npm run lint` (ESLint, then `npm run format:check` through its `postlint` hook), `npm run test`, `npm run build`, `npm run e2e` for the app; `npm run factory:typecheck` and `npm run factory:test` for the factory; `node factory/dev-rehearsal.ts --dry` for the end-to-end method rehearsal.

Always run tests through the wrapped npm commands, never `npx vitest`/`npx playwright test` directly: the wrappers auto-clean transient artifacts (`.next-e2e-*` dist dirs, `test-results/`, `playwright-report/`) after the run, including Playwright's post-teardown `.last-run.json` that the config-level teardown cannot catch. Targeted runs pass through: `npm test -- <test files>`, `npm run e2e -- <spec> --project=<project>`.

This repo pins Next.js 16, which has breaking changes from older releases — confirm App Router APIs and conventions against the bundled docs in `node_modules/next/dist/docs/` rather than from memory.

## Method invariants (bind every change to this repo)

The workflow contract is implemented and locked by tests; **the code is the contract** — never maintain a sidecar document that re-describes what the project is (the durable "why" lives here, the rest lives in code, tests, and `git log`). This repo is **public**: the local method backlog (`TASKS.md`) stays gitignored, and nothing session-internal gets committed. Before any sizable evolution: state-of-play audit of the existing engine by an agent team first, then evolve the audited modules — never restart from zero, never overwrite working machinery.

These are the standing principles — the "why" a diff cannot derive from the code alone. Any change that violates one of these is wrong even if every gate stays green:

- **P1 — No fakery.** Every safety/traceability/coverage/progress mechanism must be genuinely verified and enforced by the orchestrator. A report, matrix, or hash that nothing downstream checks is forbidden. Deterministic wherever possible.
- **P2 — Zero humans in the development loop.** Exactly one legitimate human touchpoint exists: the owner decision on a Change Request. Retry buttons are human interventions *on* the machine, never steps the machine waits for. Every operational input the loop needs is machine-established, never hand-edited — the verification gate command (`vivicy.json#gateCommand`) is written as the `null` sentinel by scaffold/import and filled with a real command mechanically: the extractor states it from the canonical for the orchestrator to record, else the stack-setup issue's implementer establishes it under an injected directive that the orchestrator validates before any gate runs.
- **P3/P4 — Loud failures, no blind states.** On any detected problem the orchestrator remediates automatically within bounded attempts, then blocks loudly (report + notification). Being silent about what happened, where, or why is forbidden; the loop always progresses or surfaces a block.
- **P5 — Flexibility inside determinism.** Judgment lives in agent legs at decision points (readiness verdicts, proof verdicts); the orchestration around them stays deterministic and evidence-based. Enforcement of rules is always the orchestrator's, never the agent's.
- **P6 — ShadcnUI only.** All UI comes from shadcn primitives and tokens; nothing hand-invented in raw Tailwind.
- **P7 — Non-loop / dev-loop boundary.** Left of the boundary (spec intake: import, Vivi) there is no automatism — only user ↔ Vivi. Right of it, everything is autonomous. UI must preserve and display this boundary.
- **P8 — Stage typing.** Every workflow stage is typed deterministic / agent / mixed (`components/workflow/workflow-stages.ts`); a new stage declares its type and the UI shows it.
- **P9 — A notification exists only if it pushes the owner to DO something.** One is written iff it asks for an owner action (decide a CR, fix a red gate or a refused write, retry, unblock) or announces a state they are waiting on from outside the app — the walk-away promise: the run finished (come taste), the run halted (come look). Anything whose honest summary is "everything worked, nothing to do" is never written — housekeeping, a phase progressing normally, a selection, a successful self-heal, a receipt for a click the owner just made: the durable record is the commit, the report and the progress ledger, and the live state is the status badge. This makes level and content agree by construction: every notification is `warning`/`error`, which is exactly what arms the Ask-Vivi pill (`isActionableNotification`, `components/chat/vivi-notifications.tsx`), and `run_finished` is the ONE deliberate `success` — the moment that asks for nothing but the owner's return. A failure is kept only where it demands an action too — `managed_files_failed` (fix the file, reopen the project) is the whole `project` family for that reason; a failure the owner can do nothing about is as silent as a success.
- **P10 — No useless work.** The canonical never chases the code; doc updates happen only when intention changes.

**Atomic verified increments — the step size is bounded everywhere the method produces steps.** Every unit of work the workflow emits — an extracted issue, a per-issue green-gate commit, a proposed CR or feature cycle — is the SMALLEST slice that still proves one behavior end to end, added without ever leaving the system broken between steps (the orchestrator commits only on a green gate, and each increment must pass its own gate alone). A spec area or an owner ask too big for one slice is DECOMPOSED into an ordered chain of gate-provable slices BEFORE implementation, never landed as one sprawling change — oversized chunks are what open the gaps, breaches, and drift. The floor is end-to-end: a slice too thin to prove a behavior on its own is wrong too, since it only moves the drift into the seams between increments. This is not a new mechanism but a bar the existing legs already enforce where each reads it — the extractor's granularity law and the fidelity verifier's granularity finding, the reviewer's proportionality signal, Vivi's slice-the-big-ask discipline — and it rides into every governed repo through the template's managed method block.

**Document preparation is the FIRST workflow stage.** Import is dumb-fast acquisition (raw files → `.vivicy/uploads/<batch-id>/`, never touched again); document preparation (`factory/prepare-docs.ts`) is what turns that raw batch into the canonical corpus the freeze then snapshots, so it runs a posteriori (the owner starts the workflow; never at import) and BEFORE extraction — hosted at the head of the extraction orchestrator, staleness-gated exactly like the supervisor's skills auto-run, because prep's outputs must exist before `doc-baseline` freezes them. **Batch↔cycle law.** A batch is bound at IMPORT to the cycle then active: the active cycle id while the canonical is pre-freeze (the project cycle before the first freeze, else the open feature cycle), or a next-cycle SEED marker while the canonical is frozen — a post-freeze import feeds the NEXT cycle, never the frozen corpus, so the gelé corpus is never silently mutated. Prep consumes ALL unconsumed COMPLETE batches of the active cycle in one run (the `manifest.json` is the completeness marker — a manifest-less batch is an interrupted write, skipped; a seed batch becomes unconsumed-active the moment its cycle opens; a batch bound to a different, non-current cycle is never consumed by another cycle's prep). Per-batch consumption is recorded append-honestly in the report (a batch is marked consumed only after all its files land, so a crash mid-prep never marks an unconsumed batch consumed). Per file, a deterministic router does the routing and an agent leg does the judgment (P5): a file already sitting under a canonical target location with a valid extension and in the dominant language is placed untouched-in-content (path a, light check only); everything else — messy docs (docx/pdf/rtf/odt text-extracted deterministically first), and any canonical-located doc in a non-dominant language — goes to the leg, which explodes/translates into canonical form (the orchestrator validates the leg's scratch output and places it; the leg writes nothing into the governed tree, W2). **Language law:** one language governs a cycle — the project's already-established canonical language, or, greenfield, the first batch of the run fixes it; every prepared output is in it and a divergent later batch is TRANSLATED toward it; uploads are never modified; there is no warning and no human language arbitration. **Prepare, don't judge:** the stage classifies, places, explodes, and translates — drift/contradiction/coherence analysis stays downstream where it already lives.

**Shared-file law.** Scaffolding a governed repo sorts every root file into three classes with three write rules (`lib/scaffold.ts`, engine in `lib/managed-block.ts`): owner files (`README.md`) are written only if missing and never edited (`writeIfMissing`, "point final"); machine files (`vivicy.json`, `.vivicy/**`) are machine-owned and created-then-owned; shared governance files (`AGENTS.md`, `CLAUDE.md`, `.gitignore`) carry exactly one Vivicy-managed block between begin/end markers (`<!-- vivicy:method:begin/end -->` for the Markdown pair, `# --- vivicy managed block … ---` for `.gitignore`) whose canonical content is single-sourced by extracting it from the greenfield template. Absent → the full greenfield template (which itself embeds the block, so re-governance is a fixpoint); present without markers → the block is appended at EOF (one blank-line separator, clean trailing newline); present with exactly one well-formed marker pair → the block is re-normalized in place — everything OUTSIDE the markers stays byte-identical to the owner's bytes, and only exact full-line marker matches count so owner text that merely resembles a marker is preserved; markers damaged by the owner's hand in any way (duplicated, unterminated, stray, misordered) → the residue is cleaned and one pristine block is put back. These four shapes are re-applied at every project OPEN too (`renormalizeManagedFiles`, called by `POST /api/project` right after the selection is persisted), not only at acquisition — otherwise a repo governed before a block-definition evolution would never receive it, since scaffolding's only production caller refuses an already-governed root. That seam is reached from BOTH directions the owner has: the picker's explicit selection, and app boot re-firing the very same POST once for the already-persisted governed project (`hooks/use-reopen-persisted-project.ts`) — a returning session resolves its project by GET and never clicks, so without the boot shot the dominant path would still never receive the evolution. The set of managed files is single-sourced in `lib/managed-block.ts` (`MANAGED_GOVERNANCE_FILES`, derived from the `MANAGED_MARKDOWN_FILES` pair every Markdown-block writer shares), which `factory/dev-loop.ts` and `factory/install-skills.ts` import by raw relative path with no bundler while the app imports it through `@/`, so that module must stay a LEAF — no Next alias and no relative value import, since none satisfies both TypeScript programs — and is server-only, the atomic writer living there. Open renormalizes the three SHARED files and nothing else: greenfield-only artifacts (`README.md`, `vivicy.json`, `.env.example`, the skeleton dirs) are never re-run, the seam issues NO git command, and neither half of it can fail the open — the function collects per-file failures instead of throwing (so the owner is told which file and why, P3/P4), and the route calls it for its effect inside its own guard AFTER the selection is persisted, since an open is not a governance action and may never be answered as an error once it has already happened. A healthy project is a zero-write, zero-notification no-op — and so is a real refresh, which announces nothing either: only a file Vivicy could NOT update reaches the owner (P9). The dirty tree a real refresh leaves is the DEV LOOP's to absorb, not the owner's to explain: `ensureCleanTreeForRun` (`factory/dev-loop.ts`) commits it as one `chore:` commit before its clean-tree gate — the way extraction's `commitSpecSnapshot` absorbs before its freeze — but ONLY when the dirty set is exactly managed governance files, with an exact pathspec so a concurrent owner edit cannot be swallowed; any other dirt still reaches the owner's verbatim dirty-tree refusal. Without that absorption the owner's next Run would be refused for bytes Vivicy wrote unasked. `ensureManagedBlock` is TOTAL — it never throws, because deleting a block whole already self-heals and punishing a half-deletion would dead-end governance for exactly the audience Vivicy serves. The ownership rule that makes repair safe: Vivicy owns a span only when its begin and end are each other's NEAREST counterpart (an end pairs with the closest begin above it, never across an intervening begin) plus any marker LINE left unpaired; every other byte is the owner's, preserved verbatim and never reordered. Pairing greedily instead would delete the owner's own lines sitting between two begin markers — including the rule hiding their secrets — so ambiguity always resolves owner-side. Editing a shared file in place to inject the indispensable rules is a legitimate P10 intention change, not useless work. **The write itself is byte-level and atomic** (`writeManaged`, the single seam every managed-block writer reaches — the scaffold's two, and the skills stage): markers and block are ASCII, so locate/splice and the equality short-circuit run over the owner's RAW bytes and any ASCII-compatible encoding — latin-1, UTF-8, a UTF-8 BOM — comes back byte-identical outside the span instead of being decoded to U+FFFD on the one path that rewrites; a UTF-16/32 file (BOM-sniffed) is refused untouched, as a typed `ManagedWriteError` carrying the owner-facing reason (`managedWriteFailureReason`, the one place Node's `, <syscall> '<path>'` tail is trimmed), through the channels that already exist — a collected failure at open, a `ScaffoldError` translated at governance start, a red skills stage — never mangled. The new bytes are written to a temp BESIDE the resolved target (the `readlink` chain, so an owner's symlinked `CLAUDE.md -> AGENTS.md` keeps its link and its target receives the block, and the rename never crosses a filesystem), created EXCLUSIVELY over a removed stale temp (a killed run's leftover must never be opened: a symlink there would capture the write, and a reused inode would carry its mode into the owner's file), carrying the target's exact mode applied to the open fd after the write since the umask masks a create mode, then `fsync`ed and published by one `rename` — data before name, or a power loss leaves the name pointing at nothing. `MANAGED_GOVERNANCE_FILES` therefore lists `.gitignore` FIRST: it carries the never-commit rules, so writing it last would leave every other managed file's temp uncovered on the very pass that installs the block; the only instant no rule covers is that first `.gitignore` write itself, whose temp predates the block by construction. Because a rename ignores the target's own mode, a read-only file — and, unlike the in-place write it replaces, a read-only DIRECTORY — is refused explicitly rather than written through. Two properties the rename does not carry, deliberately: a hard-linked second name keeps the old content, and ownership is the process's, since preserving either would mean giving up atomicity or root; a link the owner points OUT of the governed root likewise takes its temp with it, into a directory whose ignore rules are not Vivicy's to write. The `.gitignore` block's content is the never-commit set `git add -A` depends on being exhaustive — the factory runtime, per-issue worktrees, integration lock, transcripts, proof artifacts, the atomic-write temp described above, and the secret-bearing dotenv/direnv family (`.env`, `.env.*`, `.envrc` — direnv matches neither of the others), since the loop stages and pushes at every checkpoint and a brownfield repo whose own ignores miss them would have its secrets committed irreversibly. The block carries EXCLUDES only, with the proofs `recipe.txt` as the single deliberate exception: it is appended at EOF, so a `!` re-include inside it would override an owner rule above it and hand `git add -A` a file they chose to hide. The env family is therefore excluded in EVERY shape and re-included NOWHERE — not even in the greenfield catalogue below the block, because the first marker repair re-appends the block at EOF UNDERNEATH that line and flips the placeholder to ignored permanently. Greenfield instead ships a REAL `.env.example` (write-if-missing, greenfield-only — an owner's existing tree never receives a file they did not ask for) and force-adds it: into the initial commit where Vivicy inits the repo itself, and into the owner's own index where they had already init'd the target for this project (staging only — no commit and no identity Vivicy does not otherwise create). Git never ignores a path that is in the index, so a TRACKED file is immune to whatever the ignore rules later become, which is the structural end of that inversion class. The placeholder is written ONLY where that delivery is possible: a target that merely sits under a FOREIGN parent repo gets none, because staging into an index Vivicy does not own breaks the sacred-state law and an untracked one would be invisible to git forever and would state the opposite about itself — Vivicy writes nothing it cannot deliver. Generalist hygiene (`.DS_Store`, logs, editor dirs) is opinion, stays greenfield-only, and never enters the block. The method block is orthogonal to the `<!-- vivicy:skills:begin/end -->` block the skills stage maintains at the tail of the same two documents: each is owned by its own writer and one pass may only ever touch its own span, but both ride this ONE engine — a second byte-splice, a second encoding sniff, a second temp-and-rename would be a second set of guarantees to keep true.

**Cycle concurrency (project cycle singular forever; feature cycles designed-for-parallel, gated one-active).** A repo has exactly ONE project cycle — its pre-freeze life, the greenfield build of v1 — and it is never opened, never runs parallel to anything, and closes only when the first freeze snapshots it: it simply IS until then. FEATURE cycles are designed for parallelism (each drives its own issue implementation worktrees — Vivicy as a real software-development factory), but concurrency is not yet enabled: exactly one feature cycle may be open at a time. Both rules are one law, single-sourced in `lib/spec-cycle.ts#featureCycleOpenRefusal` — the only gate `lib/control.ts#openSpecCycle` and `factory/cli.ts` cycle-open open a cycle through, so the policy can never drift between app and CLI: `no_frozen_baseline` refuses opening a feature cycle while the project cycle is still live (project-never-parallel), `feature_cycle_active` refuses a second concurrent feature cycle (one-active gate) — a typed machine-facing refusal (`ControlError "cycle_state"` / CLI `EXIT_REFUSAL`, HTTP 422), never a crash. Making these guards explicit is a legitimate P10 intention (the enforcement IS the point), not useless work. Enabling parallel feature cycles later is a bounded set of cycle-keyed shapes at the sites that still resolve "the" one active cycle: the `spec-cycle.json` single-object state (→ N open feature cycles), the single `doc-prep-report.json` plus `activeCycleId`/`activeCycleKind`/`activeCycleBinding`/`unconsumedActiveCycleBatches` and the import binding (→ per-cycle report + explicit target cycle), the per-project `issue-index.json`/`done/`/progress-ledger/gates and the `run-state.json` run lock (→ per-cycle namespacing + locks), the `.vivicy-worktrees/<issue.id>` dir and `vivicy/<issue.id>` branch (→ prefixed by cycle id to avoid cross-cycle collision), and notification payloads (→ a cycle discriminator). The batch↔cycle binding, per-cycle language, and the frozen-baseline chain (`approval_ref` = cycle id) are already cycle-keyed; lifting the `feature_cycle_active` gate plus a concurrent scheduler is what flips the switch.

## Truth model (why CRs exist, and when direct edits are legal)

One source of truth per type of truth: product intention = canonical spec + accepted CRs; work to do = issues; real result = code + tests; conformity proof = gates + traceability. Issues and code are never the product truth. The current product contract = the latest frozen canonical baseline + accepted CRs not yet folded in; an accepted CR must eventually be folded into the canonical (never an old spec plus infinite annexes).

**Spec kinds and cycles.** A governed project's life is an ordered chain of spec CYCLES: at most one **project** spec (greenfield — the repo carries no product code when the spec starts) then any number of **feature** specs (evolutions of the existing codebase), one active at a time. The kind is detected MECHANICALLY (`lib/spec-kind.ts`, tracked files outside `.vivicy/` and the scaffold surface) and stamped into the frozen baseline manifest (`spec_kind`) — never an agent's judgment. Between two builds, opening a feature cycle (`lib/spec-cycle.ts`, the `.vivicy/development/reports/spec-cycle.json` state file) is the official mechanism for evolving the canonical: it reopens Vivi's pre-freeze allowlist, the supervised build is refused while it is open, and the NEXT extraction freeze (a MINOR version bump, `approval_ref` = the cycle id) closes it mechanically — a cycle is never closed by declaration. Mid-build intention changes remain CRs (rule 3 above); post-delivery feedback triages into CRs (conformity) or the next feature cycle (new intention). Cancelling a cycle is legal only while the canonical still verifies against the frozen baseline.

The four routing rules, all enforced in code (`lib/vivi.ts` allowlists, `factory/change-control.ts`, `factory/cr-apply.ts`, the readiness leg):

1. Ambiguity found during extraction (pre-build): fix the spec directly, re-freeze, re-extract — no CR.
2. A spike discovers a real constraint post-freeze: CR mandatory — the spike proposes, never edits the spec (pre-freeze spike proving may edit directly).
3. The need changes during development: CR mandatory — the official mechanism for "the initial intention is no longer right".
4. An issue becomes non-implementable because of already-produced code: execution-plan problem → modify the issue only; intention problem → CR toward the spec. A CR whose application touches the canonical always forces a re-freeze.

## Per-leg timeouts (agent legs cannot hang the loop)

Every agent leg (both the dev-loop's implementer/reviewer and the extractor/verifier) runs through the shared spawn infra (`factory/agent-spawn.ts` → `factory/leg-timeout.ts` → `factory/leg-supervisor.ts`) under TWO independent watchdogs, so a wedged `codex exec`/`claude` (alive but producing nothing) can never block the orchestrator:

- a **hard wall-clock cap** (`VIVICY_LEG_TIMEOUT_MS`, default 45 min) — the absolute ceiling for one leg, generous enough for legit xhigh-effort issues (15–30 min);
- a **stall/idle timeout** (`VIVICY_LEG_IDLE_MS`, default 12 min) — no new stdout/stderr for this long means the CLI is wedged even before the cap.

Whichever trips first kills the leg's **whole process group** (SIGTERM, then SIGKILL after `VIVICY_LEG_KILL_GRACE_MS`, default 10 s) — the CLI spawns children, so the group kill leaves no orphans — and returns a structured timeout failure (`timedOut: true`, a human reason, a non-zero status). The dev-loop and the extractor both treat a timed-out leg as a FAILED attempt inside their existing bounded retries (retry the issue; if it keeps timing out, record `issue_blocked` / `extraction_blocked` naming the timeout — never hang). Set any of the env values to `0` to disable that watchdog. The verification gate (the target's `vivicy.json` `gateCommand`, e.g. `go test ./...`, `cargo test`, `pytest -q`, `npm test`) is NOT an agent leg and is not subject to this policy.

## Public-API quality bar (where it lives, and why no dead-code gate)

Two classes of defect live in the seams of the per-issue two-agent loop and are NOT caught by the deterministic gates (which prove coverage, traceability, and that the project's own test command exits 0):

1. a public function that works only via a side-channel hack, backed by a dead exported symbol that production never calls and a unit test that exercises a hand-built input instead of the real public path; and
2. a public entry point that throws a raw `TypeError` on garbage input (`null`, wrong-type, …) because the "never throws / typed error" invariant was only tested for valid-shaped failures.

These are addressed in the **role prompts**, not by new deterministic checks. The implementer prompt (`factory/prompts/implementer.md`, "QUALITY BAR") requires, for any issue touching a public API/boundary: end-to-end testing through the real public entry point (not just internal helpers), type-fuzzing each public boundary to its documented typed degradation, no side-channel reconciliation of a contract conflict (STOP and route to change control instead), and no dead/unreferenced exports. The reviewer prompt (`factory/prompts/reviewer.md`) carries the matching MUST-fail checklist, including a cross-check against ALL canonical docs that touch the feature. The extractor's independent fidelity verifier (`factory/prompts/extraction-verifier.md`) adds a cross-document consistency check so a spec that describes the same data shape two ways is reconciled BEFORE implementation, not by the implementer at build time. `factory/dev-loop.test.ts` locks these prompt invariants so they cannot be silently dropped.

**No deterministic dead-export gate.** We deliberately did NOT add an "unreferenced export" check to the gate. Vivicy is language- and project-agnostic, and a robust detector needs per-language call-graph reachability from declared entry points plus a declared public-API surface to avoid false positives. Without those, a grep/regex "referenced only inside its own module + tests" heuristic flags every legitimate public-library export (the API surface is unreferenced internally by design) and misses the actual audit defect (its dead export WAS test-reachable; the real signal was "not on the production path"). That tradeoff is noise without coverage, so the reviewer checklist — which has the semantic context to tell a genuine dead export from an intended public one — owns this instead.

## Test matrix (mandatory upkeep)

`test/TEST-MATRIX.md` (committed) is the exhaustive inventory of every test case — covered and GAP — for the whole system, organized by area plus cross-matrices. **Every change that adds, changes, or removes behavior MUST update the matrix in the same working session**: add new cases at the next free id in the right area, update the scenario/expected text of changed ones, delete cases for removed behavior (ids retire, never get reused), flip `GAP` to the covering test reference when you write one, and adjust the status table counts for the touched areas. Case ids are stable and never renumbered. A behavior-touching session that ends without reconciling the matrix is incomplete work.

This mandate is machine-verified (P1): the matrix header carries a `Reconciled fingerprint:` over the behavior-bearing source tree plus the HEAD commit hash at reconciliation, and `scripts/test-matrix.test.ts` (in the vitest suite, so `npm test` runs it) fails when the code changed without a re-stamp — printing the exact behavior files changed since the stamped commit (`git diff` + dirty tree) — when the status-table counts drift from the actual bullets/GAPs, or when case ids collide. After reconciling the matrix — including after a pure no-behavior refactor — run `npm run matrix:stamp`; the stamp is the explicit declaration that the reconciliation happened, and `git log test/TEST-MATRIX.md` is its audit trail.

The reconciliation itself is agent work with a git-derived work-list: `npm run matrix:delta` prints exactly the behavior files changed since the stamped commit — read those files, reconcile their cases, recount, stamp. Stamping without doing that reading is falsifying the declaration; never do it.

Repo skills live under `.agents/skills/` (committed, standard SKILL.md format — the same convention Vivicy's own skills stage installs into target repos). Every agent must follow them when their trigger applies; this list is their registry:

- **matrix-reconcile** ([.agents/skills/matrix-reconcile/SKILL.md](./.agents/skills/matrix-reconcile/SKILL.md)) — reconcile `test/TEST-MATRIX.md` from the git delta; trigger: the matrix guard is red, a behavior change is about to be committed, or the matrix is being updated for any reason.

## The golden rule — every artifact earns its keep by driving behavior

Everything this repo carries — every doc, prompt, directive, comment, and line of code — must drive what an agent or a human DOES; content that only reassures rots into a stale lie, so delete it rather than write it. This never deletes a contract: a quality bar, a security boundary, or a cross-process invariant CHANGES behavior and is kept, even hardened. And the rule bounds WRITING, never observation: be exhaustive in reading, search, and verification — token economy never trumps evidence, a partial observation is a false observation — and minimal only in what you add.

**Zero comments by default.** The code, its names, and its tests are the documentation. A comment may exist ONLY when it states a structural invariant, constraint, or danger that is **not derivable from the code itself** — the "this breaks if you change it" class: a cross-process byte-compatibility contract, a deliberately non-obvious ordering, a platform trap, a security boundary. One dense line, no story. The canonical set of such invariants lives in the "Structural invariants" section below — prefer pointing there over repeating them inline. Never write: narration or paraphrase of the next line, JSDoc/docstrings that restate names and types, module-header essays, decorative banners. Tool directives (`eslint-disable`, `@ts-expect-error`, `"use client"`, shebangs) are not comments — keep them. When editing a file that still carries legacy comments, delete them as you pass.

**No backward compatibility before the first public release.** Vivicy has never shipped and governs no production repo, so nothing on disk predates the current code: a contract change is made CLEAN — one format, one reader, one writer — with every fixture re-frozen onto it and the dead shape refused where a validator exists, never tolerated by a dual-format reader, a renamed-key alias, a default-backfill, or a migration shim. A mechanism that serves the FUTURE product (managed-block renormalization, error-tolerant parsing of user- or agent-authored input, degradation on a file that never had another spelling) is not compatibility and stays.

**Never encode a moment in time.** The ban on time-fixed references extends beyond comments to the code itself. Code is a flow — it states what the system IS, never when or in which batch a piece was written. Do not encode version markers, plan/workstream/sprint/phase codes, "new/old/legacy/added in vX" wording, or session references in identifiers, strings, file names, comments, or docs. Version data a machine reads is functional, not a marker (dependency manifests, protocol/schema version fields, the semver in `package.json`) — it stays.

`npm run lint` enforces this mechanically: a custom rule (`scripts/eslint-comment-density.ts`, wired in `eslint.config.mjs`) caps per-file comment density across the whole repo including `factory/`, calibrated to the invariant-only baseline — narration-level commenting fails the gate.

## Structural invariants (the non-derivable "why"s — the only sanctioned comment content)

**CLI ↔ app parity**
- `factory/cli.ts`, `lib/control.ts` – never import each other; parity holds only because both spawn the identical factory scripts/args and read/write the same state-file schemas (`run-state.json`, `skills-install.lock`, `doc-prep.lock`, `notifications.jsonl`, `current-project.json`), never shared code beyond the dual-program LEAVES below that own a path or a lock protocol outright (`lib/project-runtime.ts`, `lib/stage-lock.ts`).
- `lib/project-runtime.ts` – single derivation of project-scoped runtime/lock paths, imported identically by the Next app and by `factory/cli.ts` via a raw relative import with no bundler, so it must stay free of `@/` aliases and Next-only imports; this is what makes a CLI-started and a UI-started run agree on one lock.
- `lib/control.ts` (`claimRunLock`), `factory/cli.ts` (`claimCliLock`) – every lock a CLIENT owns is claimed with the fs `wx` exclusive-create flag before spawning, never written unconditionally, closing the check-then-spawn TOCTOU window both clients depend on.
- `lib/stage-lock.ts` (`claimStageLock`, `stageLockHolder`), `factory/install-skills.ts` (`openStageTree`, `settleStageTree`), `lib/control.ts` (`refuseWhileSkillsStageHolds`), `factory/cli.ts` (`skillsStageInFlight`) – the skills stage claims `skills-install.lock` ITSELF, inside the process that does the writing, so the supervisor's own child, the app's detached spawn, the CLI and Vivi all inherit ONE refusal instead of each claiming for itself: the claim rides `openStageTree` and is released by `settleStageTree`, the same `finally` that closes the absorption on the return AND the throw path. The clients only PROBE that one file — read-only, with their own liveness source injected — and refuse fast with the typed `already_running` (HTTP 409, `EXIT_REFUSAL`) the routes already map; a dead heat between two spawns is then decided by the child's exclusive create, which is why a caller-side claim would be wrong here and not for the run lock: a DETACHED caller cannot release what it claimed. A lock whose recorded holder is gone is a killed stage's residue, and breaking it is IDENTITY-guarded, never freeing the path to establish that identity: the residue is hard-linked aside under a per-process name FIRST, the LINKED bytes must be the residue that was inspected, and the unlink of the lock path is the LAST act, gated on two re-proofs taken immediately before it — the `.break` marker still names THIS process, and the lock path is still the very entry that was linked. A competitor can claim that path between the liveness read and the break, so a break that MOVED the file away to inspect it would leave the path free, for the length of one read, to a third party's exclusive create and would then delete the claim it was holding — a best-effort restore cannot close that, since the restore is exactly what fails when someone took the path. And an unlink names a PATH while the proof is about an inode, so a breaker that already replaced the lock path while this one was verifying must be caught by the entry re-proof rather than assumed away. Those two re-proofs are where the containment lives, and they are what a breaker robbed of its marker or overtaken on its path stops at. The `.break` marker narrows how often a second breaker exists but does NOT guarantee one at a time: a taker that REFUSES destroys nothing, while a taker that SUCCEEDS unlinks by path, so two takers of one abandoned marker can both pass their own re-proofs and the second's unlink can remove the first's freshly published marker. Every ordering that a scheduler produces is caught downstream by those re-proofs; what is left needs two simultaneous one-syscall stalls in two processes, and it is carried as a measured residual (`cli-supervisor-process-infra.557`) rather than closed, because POSIX offers no compare-and-swap on a path and a second-level token would only move the same window one level down. It is PUBLISHED atomically (bytes written to a per-process temp, then `link`ed into place), because an exclusive create is an open and a write and a kill between them would leave a PARTIAL marker; a partial marker reads as owned by nobody, and dispossessing a live breaker is the one thing the destructive step cannot survive. An UNPARSEABLE marker therefore cannot come from this protocol at all and is treated as a foreign artifact — refused, never taken over — while a marker whose recorded owner is GONE is residue and is taken over under the SAME discipline as the residue itself — the one shape every destructive step in this module carries: the marker is hard-linked aside so its path is never freed, the linked marker must still record the owner that was judged abandoned AND still be the entry that was linked, and only then is it unlinked. A takeover that moved the marker aside to inspect it would dispossess a breaker that published in that window — the refusing taker's own cleanup deletes what it moved — so a taker that refuses must destroy NOTHING, and a killed break still cannot dead-end the stage. A break killed inside its own window leaves the claim still AT the lock path, and every per-process name it can leave — the aside link, the marker's publish temp, its takeover name — is residue marked by the pid IN that name, never by the sweeper's position, since a break can run while another process holds the lock; whichever process ends up HOLDING sweeps them (an unparseable marker included, so a foreign one self-heals), janitorially, in a way that can never fail the claim it just won. A lock that exists but cannot be READ is residue too, broken on the aside link's inode alone rather than dead-ending the stage, while a lock path that is a DANGLING symlink is refused instead: `link(2)` follows symlinks here, so no identity can be pinned for it, and removing an entry on sight is exactly how a live claim gets destroyed — nor can it ever be a holder, the exclusive create refusing an occupied path. `release` removes the file only while it still carries its own pid, so a predecessor can never delete a successor's claim.
- `factory/cli.ts` – exit codes (0 ok, 1 actionable refusal, 2 usage, 3 unexpected) are a stable agent-facing contract; never renumber or repurpose them.
- `factory/cli.ts` – target resolution is env/flag-only and deliberately never reads the UI's persisted `current-project.json`, so a CLI run can never silently act on whatever project the UI last picked.

- `factory/dev-loop.ts`, `factory/project-config.ts`, `factory/extract-issues.ts` – the verification gate command always comes from the target project (`issue.gate_command`, else the target's `vivicy.json#gateCommand`), never a hardcoded Node/npm default; `gateCommand: null` is the sentinel for *not yet established* (scaffold/import write it, never a human) and the workflow fills a real command mechanically — the extractor records an explicitly-canonical-stated command via `.vivicy/development/reports/extraction-gate-command.json`, else the stack-setup issue's implementer establishes it under a directive injected while the sentinel stands, and the gate refuses to run (issue blocks, never marked done) until it is gone and non-empty. `vivicy.json` is the ONE declaration location — no `package.json#vivicy` fallback is read for any field.
- `factory/dev-loop.ts` (`proofsDirective`, `declaredProofsPresence`, `resetDeclaredProofArtifacts`, `proofsOutcome`), `lib/proofs.ts` – a declared proof's artifacts resolve through `abs()`, the MAIN target root, never the leg's worktree (exactly like transcripts): a worktree-local capture dies with the worktree at integration, which is why the injected directive hands the leg an ABSOLUTE home outside its tree. The orchestrator clears that home (all but the recipe) before every attempt so presence can only witness the closing run, then checks presence and nothing else — and a home the clear did NOT win is missing by construction, never inspected, since what survived there may be an earlier attempt's observation. Of the home, git keeps exactly one file — each proof's `recipe.txt`, re-included by the managed ignore block — because an observation nobody can replay is not a proof; the declaration itself rides in the committed issue file.
- `factory/install-skills.ts` (`openStageTree`, `settleStageTree`), `factory/dev-loop.ts` (`ensureCleanTreeForRun`), `lib/spec-kind.ts` – the skills stage absorbs its own writes into ONE commit, from a `finally` so a return and a throw are both closed paths, because the dev loop's clean-tree absorber takes `MANAGED_GOVERNANCE_FILES` and nothing else — an unabsorbed stage refuses the owner's Run for bytes Vivicy wrote unasked — and because per-issue worktrees are cut from HEAD, which makes that commit the ONLY channel delivering the bundles and the skills block to a leg. What it stages is neither `-A` nor the declared footprint but the intersection of two narrowings, read in ONE key space — the snapshot resolves each managed document's symlink chain exactly as the writer does (`resolvedManagedTarget`), or a document linked to another in-repo file would be dirty under a name the declared paths never mention and the owner's uncommitted bytes there would ride the commit — and BOTH are load-bearing: what this RUN actually wrote (the report and the pruned skeleton `.gitkeep`s always, the lockfile and a `.agents/skills/<skill>` + per-agent links per skill it installed or removed, the bundle alone for a skill a maintenance pass RESTORED — its links point at that directory and survive the rename — and `AGENTS.md`/`CLAUDE.md`/`vivicy.json` only when it rewrote them), MINUS everything a pre-stage `git status` snapshot already found dirty. `.claude/skills` and `.agents/skills` are where an owner keeps their OWN skills and the three governance files carry owner bytes the stage merges into, so the declared footprint alone commits their manuscript, while the snapshot alone still loses the race against a detached run — an owner file created mid-install is dirty and not in the snapshot. Dirt that IS theirs stays uncommitted and the dirty-tree refusal on it is correct behavior; the zero-human law governs the skills lifecycle, never the absorption of the owner's uncommitted work. Both git commands take that exact path set through stdin (`--pathspec-from-file=- --pathspec-file-nul`), and the commit carries it too (`--only`): argv has a ceiling a bundle's file count does not, an untracked DIRECTORY entry would be re-globbed at add time, and a pathspec-less `git commit` rides the whole index — including the `.env.example` `lib/scaffold.ts` stages deliberately without committing. The absorber acts only on a repo the target itself roots (`rev-parse --show-toplevel`, both sides realpath'd), or a target nested under a foreign parent repo would have its skills written into that owner's history. The per-agent links the `skills` CLI writes are repo-relative today (measured); a machine-rooted one, for a skill THIS run wrote, is rewritten before the commit — through the `.vivicy-tmp.` rename the managed ignore block already covers — since history must not carry one machine's paths. Because the commit makes that footprint TRACKED, `lib/spec-kind.ts` excludes it from `isCodeEvidence` (and hosts the path constants the stage imports, being a leaf module both the Next program and plain node load): counting it would flip a greenfield repo to `feature` on the first install and stamp that kind permanently into the frozen manifest.
- `factory/install-skills.ts` (`projectInstalledSet`, `writeSkillsBlock`, `skillsStageNeeded`) – the skills report's `installed` is the project's FULL installed set at every phase of every path (auto, explicit, remove, skip), and the skills block is a PROJECTION of that same value rather than a second computation of it — a report and a block disagreeing about which skills a project has is a lie no downstream reader can resolve, and the surfaces that showed it (the sidebar card, the workflow evidence, the summary counts) each read one of the two. The run's own contribution lives in `added`/`removed` instead, which is what the human-facing counts name ("N installed … this run; project total T/6"). The set is the ids of vivicy.json's `skills` declaration unioned with the prior report — already the `not_installed` refusal's definition of installed, and defence in depth since the declaration writer silently no-ops on an unparseable vivicy.json — plus this run's installs minus its removals, so a hand-declared id joins both surfaces on the next settled run. That raw union answers MEMBERSHIP only: every COUNT and every budget — the cap slice, the `cap_exceeded` detail, the at-capacity no-leg gate, and the remaining-slot sentence the scout reads (`remainingSlots`, the one derivation) — reads the projected SET instead, because the union keeps ids the set drops for naming no skill, and an owner typo in the `skills` declaration would otherwise invent a slot: a five-skill project would fire the at-capacity gate, stamp `selection_baseline_id`, and permanently cancel its own scouting while the report published 5/6. The block goes to the SAME file set as the method block (`MANAGED_MARKDOWN_FILES`) through the SAME engine (`writeManaged`) — two CLIs read two documents, and a brownfield `CLAUDE.md` that points nowhere would otherwise never learn the project has skills — so write-if-different, marker repair, encoding refusal, symlink survival, mode and the atomic publish are all the engine's and are never reimplemented here; the stage adds only what is its own: the causal `recordWrite` taken from inside the engine's `onWrite`, on the one path that publishes (recording a path the stage did NOT write would put an owner's mid-run edit into the absorption commit), the guard that never CREATES a block for a project with no skills, and each bullet's `.agents/skills/<skill>/SKILL.md` — the leg's one actionable instruction, a code span and not a link so a declared-but-uninstalled bundle cannot red `reference-check`. A document that REFUSES the block ends the stage `failed`, naming the file and the reason: the skills are installed and declared but no leg reads them until the block lands, and reporting green would be a lie while throwing mid-phase left the report stuck in flight. A converged document is never written at all, which is what lets even the zero-write skipped path converge a hand-declared id without a read-only file failing anything. Settling is separate from reporting: `selection_baseline_id` is written by the AUTO path alone and `skillsStageNeeded` reads nothing else, so one explicit install or a removal can never cancel the automatic scouting a baseline still owes — the predicate lives with the writer and the supervisor imports it, because the stage's own skip and the supervisor's gate must be the same question asked once.
- `factory/skill-pin.ts`, `factory/skill-heal.ts`, `factory/install-skills.ts` (`maintainSkills`), `factory/project-config.ts` (`updateProjectConfig`) – an installed skill is PINNED, and the pin lives in `vivicy.json#skills` (`{id, bundle_hash, files}`) rather than in the skills report, because the report is one stage run's artifact while the pin is the project's standing declaration of the bytes it agreed to run: ids and hashes are ONE list, so a declaration and a pin cannot desync, and an entry carrying only an `id` is the owner's hand-declaration (declared, unpinned, verified by nothing). No `version` field ANYWHERE, including in the upstream probe: `skills add` takes no ref and serves latest, its `skills-lock.json` carries `{source, sourceType, skillPath, computedHash}`, and the registry's only unauthenticated endpoint is the audit one (all measured), so the sole comparable notion of "newer" is CONTENT — the bytes upstream serves now against `bundle_hash` — and a version field would be a value nothing could produce or read. The VERDICT is `bundle_hash` alone; `files` only names which file moved. Letting the per-file map decide would hand a hand-edited manifest entry a bundle that re-drifts on every pass — a heal, a commit and a report write at every supervisor start, forever. Its values are tagged (`sha256:` for a file, `symlink:` for a link's target, `unsupported:` for anything else) because a bare hex cannot tell a file from a symlink whose target text hashes the same, and the walk is TOTAL for the same reason: an entry it skipped is where a tamper hides — which is why every map keyed by a FILENAME here is prototype-free, an assignment to `__proto__` on a plain object being a silent no-op that would drop a bundle-root file of that name out of the manifest, the hash and the verdict at once. Empty directories are invisible, which is exactly what makes the on-disk walk and the git-history rung agree without a rule. Self-heal is a ladder in cost order — the machine-local content-addressed cache under the project's gitignored runtime dir, then this repository's own history (`GIT_INDEX_FILE=<temp> git --work-tree=<scratch> checkout HEAD -- <bundleRel>`, which leaves the real index and working tree untouched and carries the file modes the pin does not), then ONE re-fetch — and every rung goes through the same gate: the candidate is hashed BEFORE the bundle is touched, so a poisoned cache entry, a committed tamper or an upstream that moved on is refused rather than published, and the bundle is hashed AGAIN after the rename, since the outcome claimed is "it now matches the pin". A heal from any rung but the cache warms it, and a cache entry that does not hash to the name it is filed under is REPLACED, or the project pays the slow rung forever. **The same pass is also the update door**, because a pin that never moves means a creator's legitimate fix never reaches a governed project: for each pinned bundle that now holds exactly the bytes the pin names — verified, or restored by a rung that was not the re-fetch, since that rung succeeding IS proof upstream still serves the pin — ONE upstream fetch lands in a scratch, never in the live bundle, and its hash against the pin is the whole definition of "newer". A newer candidate goes through the SAME `fetchAudit`/`auditVerdict` gate as an install and, green, is published through the ladder's own gate, cached, and re-pinned immediately (so the window in which the declaration names bytes that are not on disk is one rename wide, and a crash inside it is repaired by the next pass's restore, the pin still being the truth); anything else keeps the pin. The owner's `VIVICY_ALLOW_UNSAFE_SKILLS` waiver is read at the INSTALL door and nowhere else — a one-time opt-in must never become standing consent, so a red update is refused even for a skill that only got in under the waiver, and the refusal detail deliberately does not mention the switch. A refused update is a `update_refused` rejection carrying its verdict and the REFUSED candidate's hash plus ONE `warning` notification (the awaited trace of that switch, the one thing here that speaks without asking for an action). "Told once" is a property of the OWNER's knowledge and not of the report being written: the record is rebuilt in PINNED order every pass so an identical outcome serializes identically and is not republished at all, and every notification this stage emits fires only when at least one entry driving it is NEW against what the prior report already announced — keyed by skill, verdict, and for an update the exact bytes refused — because a report legitimately republished for an unrelated fact would otherwise re-announce every standing refusal forever. A probe that could not answer — offline, upstream down, a candidate with no `SKILL.md` — decides nothing, leaves the previous pass's refusal standing (in the in-flight write too, which a killed pass leaves as the next one's prior), and is never itself an event; a probe that answers `current` DOES decide, so an upstream that came back to the pinned bytes clears the refusal. The probe's spawn is time-bounded, since it now sits on the hot path of every start and a blackholed network hangs at connect rather than failing fast. A bundle no rung could restore is offered no update at all: its `heal_failed` is already the owner's action item and publishing over an unaccounted drift would compound it. The bound is one upstream touch per skill PER PASS plus the ladder's own re-fetch when the pass has to undo its own publish — that second touch is accepted, not prevented, because bounding the ladder there would weaken the restore exactly when the pass has just damaged the bundle; and a heal FROM that rung is an ANSWER about upstream, so it decides the skill exactly as `current` does rather than leaving a refusal it has just disproved standing. Each skill gets exactly ONE terminal outcome per pass (`updated` > `healed` > `verified`), because a bundle cannot both hold the bytes it was verified against and hold newer ones. There is deliberately NO in-flight `updating` phase: announcing one before the probe would publish a report — and therefore a commit — at every supervisor start, which is the exact property the write-free steady state buys, while announcing it after the fetch would cover only the sub-second publish that follows. What the pass PUBLISHES is bounded by what is new, because it runs at every supervisor start and every write it makes is a commit and a notification: over a record a previous verification left it publishes only what DIFFERS from it (a bundle that stays broken is announced once, not once per start; a failure that is now fixed is cleared), and over a SELECTION's record it publishes only when it has something of its own — a restore, an update, or either one's refusal — so a project where nothing drifted and nothing moved upstream keeps the selection's summary, counts and refusals on every surface. A refusal the selection recorded (a red audit, a name collision) is carried FORWARD when the pass does publish, since it is a standing fact the owner still has to act on. The in-flight `healing` phase is published on the same terms, and a pass that published it MUST publish its terminal state or the report stays `healing` on every surface that reads it as work in progress. A bundle the pass RESTORED also leaves the pre-stage dirty snapshot: a pinned bundle's bytes are machine-owned, the restore replaces the whole directory whatever state it was in, and keeping those paths out of the absorption would leave Vivicy's own bytes dirty — refusing the owner's next Run and blaming them for it. A bundle it could NOT restore has its write record withdrawn instead, because what is still on disk there is the DRIFT: committing that would put a tamper in HEAD under a body claiming a restore, destroy the history rung the next pass reads, and ship the tampered skill to every worktree cut from HEAD. And a pass that ANNOUNCED work always publishes how it ended — byte-equality may suppress a record that repeats itself, never a phase TRANSITION, or the report keeps claiming work in progress that finished and the owner's own click is refused for the staleness window. The retry itself is never suppressed: a re-fetch runs on every start while a bundle is broken, because nothing but a retry can repair it without a human. A RESTORE never re-pins — the pin is the truth and the bytes are what gets fixed — and the only thing that moves a pin outside an install is an audited-green update; the skills block is never rewritten by this pass either, since a version bump changes no bullet in it. A held stage lock DEFERS the pass instead of refusing it (the installer is the writer of those very bytes, and the next start asks again), and an unhealable bundle is a `heal_failed` rejection plus ONE error notification naming the skill and the action, with the run proceeding degraded — zero humans in the loop means never a dead stop. `vivicy.json` has exactly one writer (`updateProjectConfig`, atomic through a temp beside the target and one rename, the target's mode carried across), because that file holds the verification gate command AND every pin: a torn write would lose both at once.
- `lib/development-overlay.ts` (`deriveDevelopmentOverlay`) – the single implementation mapping the progress ledger to `{graph_item_states, active_items}`; the extraction-time generator (`factory/generate-viewer-data.ts`) calls it with a strict `evidenceRefChecker`, the `/api/map` read path (`lib/map-data.ts`) calls it without one so stale on-disk evidence never 500s a request — it must never be forked.
- `factory/leg-deps.ts` (`legDepsForTarget`, `legDepsForVerbatimPrompt`) – the ONE `LegDeps` every stage OUTSIDE the dev loop spawns through, built from a single object literal: it roots the leg at the target repo (`abs`, `execRoot`) and pins `cwdFilter` to null. A stage imports one of the two rather than re-inlining the literal.

**Platform traps & security boundaries**
- repo-wide – any code deriving a stable key or doing path comparison from a path under the OS temp dir or a persisted target root (runtime-key hashing, e2e fixtures, test assertions) must `realpathSync` it first: macOS symlinks `/tmp` to `/private/tmp` (and `/var` to `/private/var`), so an unresolved path forks state/locks across two spellings of the same directory.
- every GIT ignore carrier (this repo's `.gitignore`, the greenfield catalogue in `lib/scaffold.ts`, the rehearsal fixtures) – `node_modules` is written WITHOUT a trailing slash: the slash restricts the match to directories, no ecosystem tracks a file of that name so it buys nothing, and the workspace/container/worktree layouts that LINK it to an install elsewhere would otherwise be untracked-and-committable by the `git add -A` the loop runs at every checkpoint; it stays greenfield-catalogue content and never enters the managed block, which carries Vivicy's own artifacts and the secret family, not one ecosystem's hygiene (`.DS_Store` is the settled precedent). `.prettierignore` deliberately keeps its slash and needs no such rule: prettier's globber never descends a symlinked directory, so its ignore rules are never consulted for one — an upstream default, therefore PINNED (`scripts/nested-checkout-ignores.test.ts`) rather than assumed, since an invariant resting on an unverified third-party behaviour would flip silently on an upgrade. That same file pins the git side against the repo's own `.gitignore` bytes. A test that spawns git to assert an ABSENCE — nothing tracked, tree clean, path ignored — MUST redirect `HOME` and `XDG_CONFIG_HOME` to an empty dir on top of `GIT_CONFIG_GLOBAL`/`GIT_CONFIG_SYSTEM`/`GIT_CONFIG_NOSYSTEM`, because git reads its default per-user excludes (`$XDG_CONFIG_HOME/git/ignore`, else `$HOME/.config/git/ignore`) whether or not `core.excludesFile` is set; a per-user rule can only ADD ignores, so it can only ever turn such an assertion green, and a machine carrying one then answers for a rule the repo does not have (measured: deleting a rule from the carrier under a hostile per-user ignore leaves the whole file green). Presence assertions need nothing — an extra ignore can only make them red. The four helpers that own this today are `lib/scaffold.test.ts`, `factory/extract-issues.test.ts`, `factory/dev-loop-supervised.test.ts` and `scripts/nested-checkout-ignores.test.ts`, each the single git seam of its file.
- `factory/cleanup-tree.ts` – removing a directory tree a just-finished child may still be flushing into cannot lean on `fs.rm`'s `maxRetries`/`retryDelay`: measured on Node 26, the racing entries spend that budget during the walk (ENOTEMPTY on the target after 20–100 ms whatever the budget, and a large `retryDelay` can still fail after the writer has already died), so convergence needs the WHOLE recursive removal re-invoked after a wait — `cleanupTree` is that one guard, it never throws (a cleanup that raised would replace its caller's outcome), and it announces through `writeSync(2, …)` because `process.stderr` is async on a pipe and drops what an exit handler writes.
- `scripts/clean-artifacts.ts`, `tsconfig.json`, `factory/tsconfig.json` – the wrapper is plain-node tooling that imports the factory primitive with a runtime-exact `.ts` specifier, which the app program rejects (TS5097) and which would drag `factory/` into the Next TypeScript program the app config excludes on purpose; it is therefore excluded from the app `tsconfig.json` and type-checked by `factory/tsconfig.json`, whose include already covers `../scripts/**/*.ts`. `tsconfig.json` must also stay strict JSON (no JSONC comments): this same wrapper `JSON.parse`s it to prune stale dist includes, and its parse failure is silently swallowed.
- repo-wide tool configs (`eslint.config.mjs`, `vitest.config.ts`, `playwright.config.ts`, `scripts/test-matrix.ts`) – every tool that DISCOVERS files by walking this tree must be blind to the nested checkouts a machine holds (`.claude/**` local tool worktrees, `.vivicy-worktrees/**` dev-loop worktrees), or the gate goes red-by-environment on phantom copies of files nobody edited: ESLint alone needs explicit `globalIgnores` patterns since it neither skips dot-prefixed segments (tsc does) nor reads `.gitignore` (prettier does — which makes the `.gitignore` entries for both dirs load-bearing for `npm run format`), vitest carries its own `exclude`, and Playwright's `testDir` plus the matrix walker's `BEHAVIOR_DIRS` are root-anchored allowlists that need nothing; `scripts/nested-checkout-ignores.test.ts` pins both opt-in ignore sets (ESLint's and vitest's), prettier's `.gitignore` reading — an upstream default, load-bearing now that `format:check` is a gate, since every tool worktree would otherwise red it on phantom copies — and the walker's blindness.
- `app/globals.css` (`@source not "../**/*.{test,spec}.{ts,tsx}"`) – Tailwind's automatic source detection scans the repo's PROSE, not just `.ts`/`.tsx`: a utility class named once in a markdown file compiles into the shipped stylesheet (measured), and that exclusion covers test CODE only. So no doc, README or matrix row may spell a live utility class name — quoting one ships dead CSS nobody renders, and quoting the witness class of `app/globals.test.ts` reds the very invariant that test exists to hold.
- `.prettierrc` (`prettier-plugin-tailwindcss`, `tailwindFunctions: [cn, cva]`) – the formatter REWRITES class-list string CONTENT: it sorts each class string into tailwind's canonical order and trims it, so a class name whose separating space lives inside a template-literal interpolation (`` `a${on ? " b" : ""}` ``) loses that space and silently concatenates into `ab`. Compose conditional classes with `cn("a", on && "b")` — one class per argument, no separator left for the sorter to eat. The same rewrite is why the one assertion that feeds a deliberately non-canonical class order carries `// prettier-ignore` (`lib/utils.test.ts`): only `cn`/`cva` CALLS are tailwind functions, so the pass sorts the assertion's INPUT and leaves its expectation untouched — the case goes red, measured, not silently vacuous. The fence is what keeps a deliberately non-canonical input from being rewritten out from under the assertion that exists to prove it survives.
- repo-wide UI components – interactive controls that must stay focusable while conceptually disabled/busy/locked (composer, send button, decision-card buttons, Radix `AlertDialogTrigger`, the one-shot Extract button) use `aria-disabled` plus a guarded no-op handler, never the native `disabled` attribute, which drops keyboard focus to `<body>` or breaks Radix's return-focus-to-trigger on close.
- `components/chat/vivi-panel.tsx` – the panel is `w-[min(100%,clamp(380px,25vw,480px))]`, never the bare clamp: the 380px floor alone exceeds every small-phone viewport (320–375; from 390 up the clamp already fits), and a `fixed` box never joins the document's scrollable overflow, so the excess is clipped off-screen unreachably and NO page-level overflow probe can see it; `100%` and not `100vw` because a fixed box resolves percentages against the viewport minus a classic scrollbar. `e2e/overflow.spec.ts` therefore measures the panel's own geometry, and bounds each descendant by the nearest ancestor that clips WITHOUT scrolling (overflow hidden/clip, or the paint containment `content-visibility` implies) — a scroller ancestor is no bound, its content being one swipe away.
- `components/chat/menu-card.tsx` – the sanctioned rounded CARD: an in-chat card is a physical object (a small restaurant menu) lying in the transcript, so it alone departs from the square shadcn card primitives (`rounded-none` on Card/Button/Input/Badge/Textarea); the rounded chrome that predates it (chat bubbles, notification rows, markdown code, sidebar sections, transcript modal, workflow widget) is a different class and is untouched, and a new chat CARD composes this base rather than inventing a rounded variant of its own — the paper/frame/turn styling has no second home. Both faces stack in one grid cell, so a card is ONE box as tall as its tallest face at every instant: swapping which face is in flow would clip the side still facing the viewer (the transcript row is paint-contained, `components/ui/message-scroller.tsx` `[content-visibility:auto]`) and reflow the thread mid-turn. Everything a card PAINTS stays inside that same box too, and that is what makes the frame read as one card: a face's hairline ring and its drop shadow both fall OUTSIDE the face's own box, so the card's ROOT reserves room for them at its outer edge — composed last, so no consumer's padding can spend it — and the turn is orthographic, with no perspective anywhere on the card, since under one the half rotating toward the viewer is projected larger and the box grows by tens of pixels vertically mid-flip, past any room a card could plausibly hold. Without both, that same containment shaves every straight edge and keeps only the four corner crescents — the area inside the card's rectangle but outside its rounded shape — which is exactly what a broken menu card looks like: detached arcs at the angles with no borders between them. A card turns to its back face only when the decision spends every action its front offered (the import card) — one whose locked buttons remain the transcript's record of the question (CR cards) keeps its front, per the `aria-disabled` rule above; the face is derived from state and the turn is armed only for the false→true transition a mounted instance witnesses, so a rehydrated transcript can never replay it, and the turn moves focus to the back face because inerting the spent side would otherwise drop it to `<body>`. `MenuCardPile` extends the same physics to a STACK: the sheets behind the live card are paper, never content (`aria-hidden`, no text), and their resting offset+rotation is static geometry kept strictly INSIDE the pile's own padding — that same paint containment shaves any rotated corner reaching past the row, so the pile is designed to fit rather than to be clipped. Its padding is the COMPLEMENT of the room the live card already reserves, never a second copy of it: a sheet's absolute inset is measured from the pile's outer edge and reaches past any padding, so the two together are what hold the sheets' peek constant; and its horizontal half is constant across the pile's whole life so the live card never changes width as the pile shrinks.

Cross-request server state therefore lives in a process-global registry (`globalThis` under a `Symbol.for` key — shared by every evaluation, gone when the process is) or on disk, never in a module `let`. Under the shipped Turbopack dev/build path the module is currently shared; the fragility is demonstrable under the webpack dev path, and the registry removes the dependency on which one is in play.
- `components/ui/sonner.tsx` – the toast stack is centred on the map CANVAS, not the viewport: it is shifted by half the live rail width (`usePanelState`, the same source the layout uses — 0 while the rail is undocked) and capped to the canvas minus a gutter, because the rail carries the process control bar (status badge, Run/Stop, Extract) and a stack that reaches it hides the state it announces and swallows the owner's next click for the whole toast duration. The scan is linear only because a FAILED closing-line search is terminal: no ``` line at or after that offset means no later occurrence of the tag can close either (each opens further in, over a suffix of the same range), so it refuses instead of rescanning the tail per occurrence — rescanning is quadratic on the ordinary markdown shape of the tag repeated mid-line (measured 4x per doubling, 16.3 s at 800 KB, worse than the regex it replaced). `lib/fenced-block.test.ts` pins all three hostile shapes at 200 000 characters, the multi-open one under a budget that separates linear from quadratic by an order of magnitude in both directions.

## Writing prose, and the formatter that keeps code honest

Markdown and prose use **natural** line breaks: one line per paragraph. Never hard-wrap prose to a fixed column — a line break is semantic (a new paragraph or list item), not cosmetic. List items stay one item per line; tables, fenced code, and intentional hard breaks are preserved as authored. Editors and Prettier must not re-wrap prose (`proseWrap: preserve`).

Code obeys the same law, enforced instead of trusted. `npm run format` and `npm run format:check` share the one `.prettierrc` over `**/*.{ts,tsx}`, and `npm run lint` runs the check through `postlint` — so a format-dirty tree reds a gate every landing already runs, while `npm run lint -- <file>` still lints exactly that file (the hook is what keeps the format half repo-wide). Every option in `.prettierrc` is the authored MAJORITY, established by re-running the whole tree under each alternative and counting: flipping any of `semi`, `singleQuote`, `trailingComma`, `bracketSpacing`, `arrowParens`, `quoteProps`, `objectWrap` or `bracketSameLine` away from what is written there dirties more files, not fewer. `printWidth` is the only option with a real trade-off — too low and it folds natural-length lines into a column (this section's law, applied to code); too high and it joins deliberately multi-line structures into monsters no human reads — so it is a measured optimum, not a preference: re-measure churn and the tree's line-length distribution before touching it, never argue it.
